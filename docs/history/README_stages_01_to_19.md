# جعبه‌ابزار مدیریت

> **مرحلهٔ ۱۹ — آزمون نهایی و آماده‌سازی انتشار.** همان کدبیس مرحلهٔ ۱۸ با ۷۳ ابزار، ۹ دسته، واژه‌نامهٔ آفلاین، تاریخچهٔ محلی با سقف ۱۰ و علاقه‌مندی ماندگار حفظ شده است. فارسی/RTL، فونت Vazirmatn محلی، لوگو و عبارت «سازنده حسین بختیاری» محفوظ‌اند. PDF همچنان طبق آزمون مرحلهٔ ۱۷ غیرفعال است.
>
> این بسته **سورس + شواهد آزمون** است؛ APK و AAB **arm64 بدون امضا** نیز واقعاً ساخته و جداگانه تحویل شده‌اند، نه انتشار امضاشدهٔ آمادهٔ نصب. **۱۷۱۶ تست Flutter و ۸ تست Python موفق**، ۱۴ capture اختیاری skip؛ تحلیل کد بدون مسئله است. Windows Release در میزبان Linux قابل ساخت نبود. وضعیت واقعی buildها و آزمون‌های اجراشده را در [گزارش QA مرحلهٔ ۱۹](../../docs/validation/stage19/README.md) ببینید. تست موفق Flutter جای اجرای Release بومی روی دستگاه را نمی‌گیرد.

## شروع سریع فعلی

**هدف:** Android 8.0+ (**API 26+**) و Windows 10/11 **x64**. **ابزار مبنا:** Flutter **3.47.7 stable**، Dart **3.13.5** و برای Android، JDK **17**. وابستگی‌ها در `pubspec.lock` قفل شده‌اند؛ بستهٔ جدید اجرایی در این مرحله اضافه نشده است.

محتوای ZIP سورس را استخراج کنید و وارد پوشه‌ای شوید که `pubspec.yaml` دارد:

```sh
flutter --version
flutter doctor -v
flutter pub get --enforce-lockfile
flutter analyze
flutter test --concurrency=1
dart format --output=none --set-exit-if-changed lib test tool
python -m unittest discover -s tool/tests -v
```

Python **3.10+** فقط برای ابزارهای QA/بسته‌بندی لازم است؛ برنامه برای اجرا به Python نیاز ندارد. نصب SDK/وابستگی‌ها و build اولیه به اینترنت نیاز دارند؛ محاسبه، واژه‌نامه و SQLite برنامه بدون شبکه کار می‌کنند. تست‌های آفلاین خودکار و محدودیت پوشش آن‌ها در [راهنمای مرحلهٔ ۱۹](../../docs/stage19_release.md) توضیح داده شده‌اند.

### اجرا در محیط توسعه

```sh
flutter devices
flutter run -d DEVICE_ID
# فقط روی میزبان Windows با toolchain C++:
flutter run -d windows
```

`DEVICE_ID` را از `flutter devices` بردارید. روی Windows به Visual Studio با **Desktop development with C++**، MSVC و Windows SDK نیاز است، نه فقط VS Code. برای Android، SDK/licenseها را با `flutter doctor -v` و `flutter doctor --android-licenses` بررسی کنید. Linux این sandbox نمی‌تواند Release ویندوز را بسازد.

### ساخت Android: APK و AAB

```sh
flutter build apk --release --no-pub
flutter build appbundle --release --no-pub
```

minSdk در `android/app/build.gradle.kts` صریحاً **۲۶** است؛ آن را برای دورزدن مشکل build پایین نیاورید. APK در `build/app/outputs/flutter-apk/` و AAB معمولاً در `build/app/outputs/bundle/release/app-release.aab` تولید می‌شود. AAB مستقیماً نصب نمی‌شود. بدون هر چهار متغیر امضای بیرونی، خروجی **unsigned و فقط برای بررسی کامپایل** است؛ fallback کلید debug حذف شده است.

امضای واقعی از متغیرهای `TOOLBOX_ANDROID_KEYSTORE`، `TOOLBOX_ANDROID_STORE_PASSWORD`، `TOOLBOX_ANDROID_KEY_ALIAS` و `TOOLBOX_ANDROID_KEY_PASSWORD` می‌آید. keystore باید **بیرون کل مخزن** باشد؛ هیچ کلید، رمز یا token را commit نکنید. روش ایجاد/تزریق امن، verify، fingerprint، نصب و تفاوت upload/app-signing در [راهنمای انتشار](../../docs/stage19_release.md) آمده است. شناسهٔ اولیهٔ برنامه و versionCode را ناشر پیش از انتشار تأیید کند.

### ساخت و تحویل Windows — EXE تنها کافی نیست

```powershell
flutter build windows --release --no-pub
python tool/package_windows.py
```

باید **تمام** `build/windows/x64/runner/Release/` با EXE، `flutter_windows.dll`، DLLهای plugin و SQLite و تمام `data/` و assets حفظ شود. ابزار، درخت کامل را به `releases/management_toolbox-windows-x64.zip` تبدیل و inventory و SHA256 ایجاد می‌کند؛ EXE تنها یا فقدان اجزای لازم را رد می‌کند. نصب VC++ runtime x64 از منبع رسمی ممکن است روی مقصد لازم باشد. این ابزار جای اجرای واقعی EXE یا بررسی امضای ناشر نیست. گواهی/PFX/private key امضای Windows هم باید خارج مخزن بماند. [ساخت، DLLها، امضا و تست نصب](../../docs/stage19_release.md).

### اگر Flutter روی دستگاه شما نصب نیست

workflow دستی [Release validation](../../.github/workflows/release-validation.yml) برای همان repository آماده است: QA روی Linux، APK/AAB **unsigned** و Windows Release با ZIP کامل روی runner Windows. آن را از Actions → Release validation → Run workflow اجرا کنید. در این محیط run آنلاین یا انتشار انجام نشده است؛ موفقیت/شکست را از خود Actions و لاگ artifactها بررسی کنید. workflow به secret انتشار دسترسی ندارد و هیچ deploy خودکاری نمی‌کند.

### آزمون و عیب‌یابی

- پوشش: موتورهای ۷۳ ابزار، فرم/مرزها، RTL، ارقام فارسی/عربی/لاتین، history ۱۱→۱۰، بازگشایی favorite، و آزمون آفلاین با منع قابل‌اثبات Dart HTTP در isolate تست.
- RAM کم: `python tool/run_test_shards.py --batch-size 1 --timeout 180 --output docs/validation/local/shards`؛ هیچ فایل تستی حذف نمی‌شود. `summary.json` باید همهٔ فایل‌ها و موفقیت همهٔ batchها را نشان دهد.
- خطای `Gradle daemon disappeared`/heap: RAM، OOM و لاگ runner را بررسی کنید؛ اجرای build/تحلیل/تست به‌طور همزمان روی ۲ GB RAM مناسب نیست.
- خطای DLL ویندوز: کل ZIP را استخراج کنید، معماری x64 و VC++ runtime رسمی را بررسی کنید؛ DLL تصادفی دانلود نکنید.
- دادهٔ محلی: در Application Support ذخیره می‌شود؛ دیتابیس کاربر را برای عیب‌یابی یا ارتقا بی‌اجازه حذف نکنید. هیچ دیتابیس واقعی کاربر همراه سورس/Release توزیع نشود.

# آرشیو توضیحات مرحله‌های ۱ تا ۱۸

**متن زیر سابقهٔ مراحل قبلی است.** جمله‌هایی مانند «هنوز پیاده‌سازی نشده» فقط وضعیت همان مرحله را توصیف می‌کنند؛ برای نصب، وابستگی، امضا و build فعلی، بخش بالای این فایل و راهنمای مرحلهٔ ۱۹ معتبرند.

> وضعیت فعلی: پایان مرحلهٔ **۱۸**؛ **۷۳ ابزار** و داده‌های قبلی حفظ شده‌اند. رنگ‌های خوانای مستقل برای ۹ دسته در روشن/تاریک، layout سازگار با متن بزرگ، فوکوس و میان‌برهای صفحه‌کلید، کاهش حرکت، صفحهٔ مستقل تاریخچه و بازبینی RTL اضافه شده است. ۲۴ تصویر تست Flutter و چک‌لیست آزمون بصری بومی آماده‌اند. راهنمای این مرحله: [`docs/stage18_ui_accessibility.md`](../../docs/stage18_ui_accessibility.md)؛ تصاویر/چک‌لیست: [`docs/visual/stage18/README.md`](../../docs/visual/stage18/README.md). PDF همچنان طبق محدودیت مرحلهٔ ۱۷ غیرفعال است. بخش‌های مراحل پیشین در ادامه تاریخی‌اند.

برنامه‌ای تک‌کاربره و آفلاین برای محاسبات مدیریت، تولید، مالی، کیفیت و دیگر ابزارهای مدیریتی، با یک کدبیس Flutter برای **Android 8.0+ (API 26+)** و **Windows 10/11 (x64)**.

## وضعیت مرحلهٔ اول

اسکلت واقعی با `flutter create --platforms=android,windows` تولید شده است. نمونهٔ شمارنده حذف شده و صفحهٔ آغازین فارسی جایگزین شده است. این بند گزارش تاریخی مرحلهٔ اول است. وضعیت به‌روز: در مرحلهٔ سوم Localization فارسی، RTL، صفحهٔ خوش‌آمدگویی و تم پایهٔ Material 3 اضافه شدند. فونت Vazirmatn، انتخاب و ماندگاری تم، محاسبات و دیتابیس هنوز پیاده‌سازی نشده‌اند.

هیچ سرویس شبکه، حساب کاربری یا backend در برنامه وجود ندارد. دریافت dependencyها و build اولیه به اینترنت نیاز دارد؛ خود برنامه قرار است آفلاین کار کند.

## نسخه‌های استفاده‌شده

- Flutter **3.47.7**، کانال **stable**، revision `abaf9c5237`
- Dart **3.13.5**
- flutter_lints **6.0.0**؛ نسخه‌های وابستگی در `pubspec.lock` ثبت شده‌اند.
- Android: مقدار `minSdk = 26` در `android/app/build.gradle.kts` تنظیم شده است؛ Java 17 مطابق تنظیمات پروژه پیشنهاد می‌شود.
- شناسهٔ اولیهٔ Android: `com.managementtoolbox.management_toolbox`؛ پیش از انتشار عمومی باید تأیید شود.

Flutter به‌دلیل کدبیس مشترک Android/Windows، قابلیت رابط فارسی و پشتیبانی ذخیره‌سازی محلی انتخاب شده است. فعلاً هیچ dependency اجرایی اضافی نصب نشده است.

## ساختار Feature-based Clean Architecture سبک

```text
lib/
  main.dart                 # نقطهٔ ورود
  app/app.dart              # ریشهٔ اپ و محل اتصال وابستگی‌ها
  core/
    errors/
    utils/
    widgets/
  features/
    home/
      presentation/pages/home_page.dart
      domain/
      data/
    calculators/{domain,data,presentation}/
    favorites/{domain,data,presentation}/
    history/{domain,data,presentation}/
    glossary/{domain,data,presentation}/
    utilities/{domain,data,presentation}/
    settings/{domain,data,presentation}/
android/                    # میزبان Android با Kotlin
windows/                    # میزبان Windows و فایل‌های CMake
 test/app/app_test.dart     # تست صفحهٔ پایه
```

Domain مستقل از Flutter و جزئیات Data خواهد بود. Data قراردادهای Domain را پیاده می‌کند. Presentation فقط منطق نمایش دارد. اتصال پیاده‌سازی‌ها در app است. پوشه‌های رزروشده با `.gitkeep` حفظ می‌شوند؛ فعلاً منطق بی‌استفاده یا repository ساختگی نداریم.

## اجرای توسعه و ساخت در محیط مناسب

Android نیازمند Android SDK، پذیرش مجوزهای SDK و Java سازگار است:

```sh
flutter doctor -v
flutter devices
flutter run -d <android-device-id>
flutter build apk --release
flutter build appbundle --release
```

پیکربندی امضای فعلی همان debug تولیدشده توسط Flutter است و برای انتشار نهایی مناسب نیست. امضای انتشار در مراحل بعد با secret خارج از مخزن تنظیم می‌شود. APK برای نصب مستقیم است؛ AAB معمولاً ورودی فروشگاه است، نه فایل نصب مستقیم.

برای Windows از **ویندوز** با Visual Studio و workload «Desktop development with C++» استفاده کنید:

```sh
flutter run -d windows
flutter build windows --release
```

بستهٔ Windows باید **تمام محتوای** `build/windows/x64/runner/Release/` شامل EXE، DLLها و پوشهٔ data را داشته باشد، نه فقط EXE. هیچ خروجی نصبی در این مرحله ساخته نشده است.

## Git و روش تحویل بدون نصب Flutter روی سیستم شما

یک مخزن Git محلی آماده شده است؛ remote یا اتصال به حساب GitHub ساخته نشده و هیچ push انجام نشده است. سورس ZIP این مرحله قابل انتقال به مخزن شماست. برای اتصال بعدی، آدرس مخزن و دسترسی مجاز لازم است؛ token یا رمز را داخل کد یا گفتگو قرار ندهید.

در مرحلهٔ انتشار، GitHub Actions می‌تواند Android را روی runner مناسب و Windows را روی runner ویندوز بسازد؛ بنابراین لازم نیست کاربر Flutter را شخصاً نصب کند. فایل‌های نهایی از **Releases → نسخهٔ موردنظر → Assets** دریافت خواهند شد. Artifactهای Actions خروجی موقت اجرای workflow هستند و با دارایی‌های Release تفاوت دارند. هنوز workflow، artifact یا Release وجود ندارد.

فایل‌های build، SDK، کلید امضا و تنظیمات محلی وارد سورس نمی‌شوند. `pubspec.lock` برای تکرارپذیری نگهداری می‌شود.

XNPV، نرخ اسمی، مالیات، تورم یا تبدیل دوره خودکار نداریم. ناسازگاری مقیاس و overflow/underflow به‌جای نتیجهٔ ساختگی خطا می‌دهد. binary64 دقت نامحدود مالی ندارد؛ علامت خروجی‌های نزدیک صفر ممکن است تحت تأثیر گردکردن باشد. خروجی توصیهٔ سرمایه‌گذاری نیست.

**Cp:** حدود مشخصات مهندسی با حدود کنترل فرق دارند؛ USL باید بزرگ‌تر از LSL و سیگمای درون‌فرایندی باید مثبت باشد. واحد همهٔ ورودی‌ها یکسان است و نتیجه بدون واحد. تفسیر متعارف به ثبات فرایند، برآورد معتبر سیگما و توزیع تقریباً نرمال وابسته است. Cp مرکزیت را نمی‌سنجد و جای Cpk/Pp نیست؛ برچسب قطعی خوب/بد داده نمی‌شود.

شرط‌های strict نرخ NPV و σ در موتور و help فارسی کنترل می‌شوند، نه با caption یک حداقل inclusive گمراه‌کننده. معادلات داخل متن مثال نیز برای جلوگیری از وارونگی در RTL با isolate جهت مشخص شده‌اند.

شرح کامل و جزئیات عددی: [`docs/calculators/stage07.md`](../../docs/calculators/stage07.md).

## مرحلهٔ ۱۰ از ۲۰ — ده ماشین‌حساب مالی

NPV قبلی بدون تغییر موتور/تعریف حفظ شد و IRR، دورهٔ بازگشت سرمایه، ROI، WACC، نسبت جاری، نسبت آنی، سود مرکب، قسط وام و نقطهٔ سربه‌سر با موتور مستقل اضافه شدند. دستهٔ مالی اکنون ۱۰ ابزار و کل کاتالوگ ۲۱ ابزار دارد. همه از همان فرم و صفحهٔ عمومی، جستجوی آفلاین، ستاره و ثبت/بازگشایی استفاده می‌کنند.

### قراردادهای مهم

- **NPV:** سرمایهٔ اولیه زمان صفر جداست؛ اولین سطر جریان نقدی پایان دورهٔ اول است. نرخ مؤثر باید متعلق به همان دوره باشد؛ XNPV یا تبدیل خودکار نرخ/ارز نداریم.
- **IRR:** فهرست برخلاف NPV شامل CF0 است. حل یکتای سری با یک تغییر علامت، با bisection روی `log(1+r)` و بازبینی باقیمانده انجام می‌شود. سری چندتغییرعلامتی با احتمال چند جواب رد می‌شود؛ حدس یا آخرین تکرار جای جواب نمی‌نشیند. نبود ریشه، دامنهٔ عددی، دقت ناکافی و عدم همگرایی پیام متمایز دارند.
- **بازگشت:** ساده و بدون تنزیل، فقط جریان خالص نامنفی؛ کسر دوره با فرض دریافت یکنواخت است. عدم بازیافت در افق داده پیام روشن دارد، نه زمان ساختگی.
- **ROI:** سود خالص پس از کل هزینه‌ها بر سرمایه‌گذاری مثبت؛ نه بازده سالانه. **WACC:** وزن بازار و سپر مالیاتی کامل بهره با فرض‌های آشکار.
- نسبت آنی موجودی و پیش‌پرداخت را حذف می‌کند؛ دادهٔ ناسازگار و بدهی صفر رد می‌شوند و آستانهٔ عمومی خوب/بد نداریم.
- سود مرکب نرخ مؤثر هر دوره می‌گیرد. قسط، وام کاملاً مستهلک‌شونده با پرداخت پایان دوره و بدون کارمزد/گردکردن قراردادی است؛ نرخ صفر مسیر صحیح مستقل دارد.
- سربه‌سر مدل تک‌محصول با حاشیهٔ مشارکت مثبت است؛ مقدار پیوسته و واحد کاملِ گرد‌شده رو به بالا جدا نمایش داده می‌شوند.
