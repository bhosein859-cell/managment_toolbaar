# مرحلهٔ ۱۶ از ۲۰ — Drift، SQLite، علاقه‌مندی و تاریخچه

ذخیرهٔ درون‌حافظهٔ مراحل قبل با Repository محلی **Drift روی SQLite واقعی** جایگزین شد. تعداد ابزارها همچنان ۶۸ است؛ موتور، فرمول و مثال هیچ ماشین‌حسابی در این مرحله تغییر نکرده است.

## رفتار قابل مشاهده

- ستارهٔ علاقه‌مندی در خانه، دسته و ماشین‌حساب، پس از commit در SQLite به‌روز می‌شود؛ افزودن و حذف پس از بستن و بازکردن برنامه باقی می‌ماند.
- دکمهٔ موجود «ثبت در آخرین محاسبات» یک snapshot مستقل ذخیره می‌کند. ویرایش زندهٔ هر رقم، بازکردن صفحه یا بازگشایی سابقه به‌تنهایی رکورد جدید نمی‌سازد. ثبت دوبارهٔ یک محاسبهٔ یکسان، رویداد تازه است و ادغام نمی‌شود.
- تا پیش از دهمین ثبت، تعداد تاریخچه همان تعداد ثبت‌هاست؛ از ثبت دهم به بعد **دقیقاً ۱۰ مورد آخر در کل برنامه** نگه داشته می‌شود، نه ۱۰ مورد برای هر ابزار. با ثبت یازدهم، شناسه‌های ۲ تا ۱۱ باقی می‌مانند. مورد قدیمی واقعاً از جدول حذف می‌شود، نه فقط از نمایش.
- ترتیب «آخرین» با شناسهٔ افزایشی درج است؛ ساعت یکسان یا عقب‌رفتن ساعت دستگاه، ترتیب را خراب نمی‌کند. زمان واقعی درخواست نیز جداگانه با دقت میکروثانیه ذخیره می‌شود.
- بازکردن یک رکورد، **ورودی خام قبلی** را برمی‌گرداند و موتور فعلی دوباره محاسبه می‌کند. نتیجهٔ زمان ثبت برای نمایش خلاصه ذخیره شده است؛ فرمول یا کد ذخیره‌شده اجرا نمی‌شود. با تغییر موتور در نسخهٔ آینده، نتیجهٔ بازگشایی ممکن است با خلاصهٔ تاریخی متفاوت شود.
- متن اطلاع‌رسانی «فقط همین اجرا» حذف و با توضیح ذخیرهٔ محلی جایگزین شده است. پیام موفقیت ثبت فقط بعد از commit نمایش داده می‌شود. هنگام عملیات، کنترل‌های مربوط غیرفعال‌اند؛ صف کنترل‌گر ترتیب درخواست‌ها را حفظ می‌کند.

## نسخه و سازگاری

نسخه‌های مستقیم دقیق در `pubspec.yaml` و نسخه‌های گذرا در `pubspec.lock` قفل شده‌اند:

| بسته | نسخه | علت |
|---|---:|---|
| `drift` | 2.35.2 | تراکنش، migration و query executor مشترک |
| `sqlite3` | 3.7.1 | موتور native بسته‌بندی‌شده با build hooks؛ بدون نیاز به DLL نصب‌شده توسط کاربر |
| `path_provider` | 2.1.6 | مسیر پایدار و خصوصی Application Support در Android و Windows |
| `path_provider_android` | 2.2.22 | pin پیاده‌سازی رسمی Android در بازهٔ مجاز بسته، برای پرهیز از زنجیرهٔ JNI غیرلازم روی desktop |
| `path` | 1.9.1 | اتصال صحیح مسیر در سیستم‌عامل‌های مختلف |

نسخهٔ Android به‌طور مستقیم و بدون dependency override محدود شده است: `path_provider` آن را به‌عنوان implementation رسمی استفاده می‌کند. این pin در بازهٔ `^2.2.5` مجاز بسته است و وابستگی گذرای JNI مربوط به سری ۲٫۳ را وارد پروژهٔ Windows نمی‌کند. پیاده‌سازی ۲٫۲٫۲۲، Java 17 و minSdk 21 دارد که با Java 17 و minSdk 26 پروژه سازگار است؛ SDK اعلام‌شدهٔ آن Dart 3.9 / Flutter 3.35 یا بالاتر است. [metadata همان نسخه](https://pub.dev/api/packages/path_provider_android/versions/2.2.22). این تصمیم برای کم‌کردن نیازهای ساخت native غیرمرتبط است، نه ادعای خرابی عمومی نسخهٔ جدیدتر.

بررسی اسناد و metadata رسمی:

- [Drift و پلتفرم‌ها](https://drift.simonbinder.eu/platforms/): `NativeDatabase` برای Android و Windows و استفاده از sqlite3 نسخهٔ ۳ بدون `sqlite3_flutter_libs` اضافی.
- [metadata دقیق Drift 2.35.2](https://pub.dev/api/packages/drift/versions/2.35.2): Dart حداقل 3.10 و sqlite3 نسخهٔ سازگار 3.x. پروژه Dart 3.13.5 / Flutter 3.47.7 stable دارد.
- [metadata دقیق sqlite3 3.7.1](https://pub.dev/api/packages/sqlite3/versions/3.7.1) و [راهنمای native assets](https://pub.dev/packages/sqlite3): پشتیبانی Android و Windows؛ کتابخانه در مرحلهٔ build همراه برنامه قرار می‌گیرد. ساخت اولیه ممکن است به دانلود asset نیاز داشته باشد؛ عملیات دیتابیس در زمان اجرای اپ آفلاین است.
- [اسکریپت ساخت همان tag sqlite3-3.7.1](https://raw.githubusercontent.com/simolus3/sqlite3.dart/sqlite3-3.7.1/tool/build_sqlite.dart): برای Android مقدار `targetNdkApi: 24` دارد؛ این پایین‌تر از minSdk=26 پروژه است.
- [path_provider 2.1.6](https://pub.dev/packages/path_provider/versions/2.1.6): Android SDK 24+ و Windows 10+، با مسیر Application Support در هر دو. محدودیت SDK بسته با Flutter/Dart فعلی پروژه هم‌خوان است.

حل dependency، دریافت با `--enforce-lockfile` و اجرای native SQLite در Linux موفق بوده‌اند. SQLite واقعی اجراشده **3.54.0** گزارش شد؛ این شمارهٔ موتور است، نه شمارهٔ بستهٔ Dart. سازگاری اعلام‌شده و حل dependency، جای ساخت و آزمون روی Android/Windows را نمی‌گیرد؛ آن ساخت‌ها در این محیط انجام نشده‌اند.

## معماری و محل فایل

- `lib/core/storage/toolbox_database.dart`: پایگاه Drift، DDL صریح، نسخهٔ schema و migrationها؛ بدون code generation یا build_runner اضافی.
- `lib/core/storage/open_local_database.dart`: گرفتن `getApplicationSupportDirectory()`، ساخت پوشه و بازکردن `management_toolbox.sqlite` در isolate پس‌زمینه.
- `lib/features/history/domain/tool_repository.dart`: قرارداد مستقل Repository و snapshot immutable، بدون وابستگی Flutter یا SQL.
- `lib/features/history/data/drift_tool_repository.dart`: queryهای پارامتری و تراکنش‌های SQLite.
- `lib/features/history/data/calculation_snapshot_codec.dart`: JSON نسخه‌دار برای ورودی خام و نتیجهٔ کامل.
- `ToolSessionController`: وضعیت مشاهده‌پذیر **دادهٔ commit‌شده**، صف عملیات، شروع/خطا/بستن؛ دیگر منبع ذخیرهٔ دائمی نیست.
- `ManagementToolboxApp`: در اجرای معمول همیشه Repository فایل‌محور می‌سازد. تزریق Repository مجزا برای آزمون‌ها وجود دارد؛ نمونهٔ تزریق‌شده نیز توسط همان اپ بسته می‌شود. استفادهٔ production از memory یا fallback بی‌صدا به آن وجود ندارد.

فایل در Application Support است، نه cache یا پوشهٔ موقت. SQLite از WAL، `synchronous=FULL`، مهلت انتظار قفل ۵ ثانیه و temp store حافظه‌ای استفاده می‌کند. اپ یک اتصال منطقی و یک worker پس‌زمینه دارد. برنامهٔ دیگری که همان فایل را تغییر دهد، اعلان زنده به این UI نمی‌فرستد؛ بازخوانی/بازگشایی داده را تازه می‌کند.

## جدول‌ها و قرارداد داده

### `favorites`

- `calculator_id TEXT PRIMARY KEY NOT NULL` با شرط غیرخالی.
- `created_at_micros INTEGER NOT NULL`، زمان epoch.

کلید ابزار یکتا است. کاتالوگ ۶۸ ابزار همچنان در کد است؛ نسخهٔ دوم کاتالوگ در SQLite ساخته نشده و FK به کاتالوگ ناپایدار نداریم. شناسهٔ ابزار حذف‌شده از کاتالوگ آینده در دیسک حفظ ولی از UI پنهان می‌شود.

### `calculation_history`

- `id INTEGER PRIMARY KEY AUTOINCREMENT`: ترتیب پایدار و یکتای ثبت؛ پس از حذف رکوردهای قدیمی بازاستفاده نمی‌شود.
- `calculator_id TEXT NOT NULL`.
- `inputs_json TEXT NOT NULL`: فیلد متنی/انتخابی با متن اصلی و فهرست عددی با آرایهٔ رشته‌ها.
- `result_json TEXT NOT NULL`: نتیجهٔ اصلی، همهٔ جزئیات، متن تفسیر، واحد، شیوهٔ نمایش و هشدارها با شدت آن‌ها.
- `created_at_micros INTEGER NOT NULL`: زمان UTC بر اساس epoch؛ ترتیب نمایش به ساعت متکی نیست.
- `payload_version INTEGER NOT NULL DEFAULT 1 CHECK(payload_version>0)`.

در payload نسخهٔ ۱، ارقام فارسی/عربی/لاتین، فاصله، ترتیب فهرست، فهرست اختیاری خالی و فیلد حذف‌شده عیناً حفظ می‌شوند. درصد خام مانند `50` دوباره با همان قرارداد فرم نرمال می‌شود، نه اینکه کسر ۰٫۵ دوباره تقسیم بر صد شود. enumها با نام پایدار ذخیره می‌شوند، نه اندیس.

## تراکنش و نگهداری ۱۰ رکورد

درج و خواندن snapshot خروجی داخل یک تراکنش Drift هستند. trigger دیتابیس `history_keep_ten` بعد از هر INSERT، همهٔ شناسه‌های خارج از ۱۰ شناسهٔ بزرگ‌تر را حذف می‌کند؛ trigger جزئی از همان عملیات اتمیک SQLite است. این invariant حتی برای درج مستقیم از اتصال SQLite دیگر برقرار است. شکست درج، trigger، حذف یا خواندن snapshot باعث rollback می‌شود؛ پیام موفقیت کاذب و حذف نیمه‌کاره نداریم. افزودن/حذف ستاره و snapshot متناظر نیز در تراکنش انجام می‌شوند.

ورودی داده به SQL با binding پارامترهاست؛ JSON یا متن ورودی به SQL/فرمول اجرایی تبدیل نمی‌شود. کلید ابزار در لایهٔ کنترل‌گر با کاتالوگ و در Repository با الگوی شناسه اعتبارسنجی می‌شود.

## migration و دادهٔ ناسازگار

نسخهٔ فعلی schema **۲** است و `PRAGMA user_version` توسط چرخهٔ migration Drift مدیریت می‌شود:

1. نصب تازه: ساخت مستقیم favorites، history نسخهٔ ۲ و trigger در تراکنش.
2. مسیر **۱ → ۲**: افزودن ستون payload_version با پیش‌فرض ۱، حذف موارد قدیمی‌تر از ۱۰ و ایجاد trigger، همگی در تراکنش.
3. نسخهٔ جدیدتر/مسیر ناشناخته: خطای صریح، بدون downgrade، حذف فایل یا ساخت دیتابیس خالی جایگزین.

snapshot نسخهٔ ۱ در `test/fixtures/storage/schema_v1.sql` **قرارداد طراحی‌شده برای تست migration** است، نه ادعای وجود دیتابیس منتشرشده در مرحلهٔ ۱۵. آن مرحله فقط حافظهٔ فرایند داشت و دادهٔ اجراهای بسته‌شدهٔ آن قابل بازیابی نیست. fixture مستقل نسخهٔ ۲ نیز برای مقایسهٔ introspection نصب تازه و schema مهاجرت‌شده وجود دارد. تغییر schema یا payload در آینده باید با افزایش نسخه، مسیر تبدیل صریح و آزمون تازه همراه باشد.

JSON خراب یا نسخهٔ payload ناشناخته به خطای خواندن تبدیل می‌شود؛ رکورد با مثال پر یا دیتابیس خودکار reset نمی‌شود. خطای شروع، صفحهٔ فارسی با تلاش دوباره دارد و حالت خالیِ ظاهراً موفق نشان نمی‌دهد. retry اجرای معمول، opener شکست‌خورده را از نو می‌سازد. خطای نوشتن، وضعیت commit‌شدهٔ قبلی را نگه می‌دارد و در صفحهٔ فعلی نمایش داده می‌شود.

## آزمون و گزارش واقعی

گزارش‌ها در `docs/validation/stage16/`:

- `flutter analyze`: **No issues found**؛ قالب‌بندی **۲۳۸ فایل، بدون تغییر**.
- آزمون متمرکز ذخیره‌سازی و کنترل‌گر: **۱۲۱ موفق**، شامل ۲ آزمون به‌روزشدهٔ session قبلی.
- آزمون کامل: **۱۳۲۷ موفق، ۱۳ skip اختیاری ثبت تصویرِ مراحل قبل**؛ بدون شکست.
- codec روی مثال واقعی **هر ۶۸ ابزار**: ورودی، نتیجه، آرایه‌ها، واحد و هشدارها round-trip می‌شوند.
- Repository: ثبت ۱ تا ۱۱، سقف سراسری میان ابزارها، درج هم‌زمان ۳۵ مورد، تساوی/عقب‌رفتن ساعت، toggle سریع، یکتایی ستاره، حذف پایدار و immutable بودن snapshot.
- migration: فایل واقعی SQLite نسخهٔ ۱ با ۰/۱/۱۰/۱۱/۱۵ رکورد، حفظ payload و زمان و علاقه‌مندی، مقایسهٔ schema با fixture مستقل، rollback خطای مهاجرت، نسخهٔ جدیدتر و فایل خراب.
- rollback با تزریق خطای trigger حذف: درج یازدهم و حذف قدیمی هر دو برمی‌گردند؛ ۱۰ رکورد قبلی و شمارندهٔ ID سالم می‌مانند.
- در رویداد ثبت، ورودی و نتیجه در همان لحظه دوباره خوانده می‌شوند؛ آزمون تغییر/نامعتبرشدن ورودی پیش از frame بعدی مانع ذخیرهٔ ترکیب ورودی تازه با نتیجهٔ کهنه است.
- widget: بستن کامل اپ و اتصال، ساخت اپ تازه با همان فایل، حفظ ستاره و بازکردن ورودی ۵۰٪ با نتیجهٔ ۴۶٫۵۵٪؛ همچنین خطای شروع/تلاش دوباره و خطای ذخیره بدون پیام موفقیت کاذب.
- smoke مستقل فایل‌محور در **سه فرایند جداگانه**: write، read-remove و verify-removed؛ هم با `dart run` و هم bundle بومی لینوکس موفق.
- ۹ smoke موتور قبلی موفق‌اند؛ تعداد و محاسبات ۶۸ ابزار حفظ شده‌اند.
- پوشش خط فایل‌های ذخیره‌سازی/کنترل‌گر در `coverage.md` ثبت شده است؛ پوشش خط، اثبات درستی همهٔ شاخه‌ها نیست.

لاگ آزمون opener شکست‌خورده ممکن است هشدار debug شمارندهٔ چند نمونهٔ Drift را نشان دهد: opener اول پیش از ساخت اتصال native شکست خورده و اتصال بسته‌نشدهٔ هم‌زمان به فایل یکسان وجود ندارد. هشدارهای چند نمونهٔ عمدی با executorهای مستقل در دو تست دیگر فقط در محدودهٔ همان تست‌ها غیرفعال‌اند، نه در production.

### دستورهای بازتولید

```sh
flutter pub get --enforce-lockfile
flutter analyze
flutter test
flutter test --coverage test/features/history test/features/home/session_test.dart
# db-path باید تازه باشد؛ هر دستور یک فرایند مستقل است.
dart run tool/verify_local_storage.dart write /path/to/new.sqlite
dart run tool/verify_local_storage.dart read-remove /path/to/new.sqlite
dart run tool/verify_local_storage.dart verify-removed /path/to/new.sqlite
# برای AOT دارای asset بومی از build cli استفاده شود:
dart build cli --target=tool/verify_local_storage.dart
```

`dart compile exe` به‌تنهایی کتابخانهٔ SQLite را کنار smoke قرار نمی‌دهد؛ اولین اجرای آن بدون asset شکست خورد. مسیر صحیح `dart build cli` با پوشهٔ `bundle/bin` و `bundle/lib` اجرا و در `storage-aot.txt` ثبت شده است. این بررسی AOT لینوکس است، نه build اپ Android/Windows.

## حدود امنیت و تحویل

SQLite این مرحله **رمزگذاری نشده** و ورودی‌های محاسبات در فایل محلی‌اند؛ دسترسی با مجوز پوشهٔ کاربر/برنامه محدود می‌شود. حذف دادهٔ اپ، حذف فایل یا uninstall ممکن است اطلاعات را از بین ببرد. برنامه همگام‌سازی شبکه‌ای یا backup اختصاصی ندارد؛ رفتار backup سیستم‌عامل جداست. دوام مورد تأیید مربوط به تراکنش commit‌شده است، نه عملیاتی که هنگام قطع فرایند هنوز تمام نشده است.

APK، نصب‌کنندهٔ Windows، اجرای روی دستگاه واقعی، تصویر تازه، push به مخزن یا انتشار انجام نشده‌اند. بستهٔ تحویل سورس، قفل نسخه، fixtureها و گزارش‌های اجراست. ساخت روی پلتفرم هدف و بررسی مسیر/مجوز/بسته‌بندی native asset در release واقعی همچنان لازم است.
