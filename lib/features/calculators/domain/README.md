# قرارداد Domain ماشین‌حساب‌ها — مرحلهٔ ۵

این کتابخانه Pure Dart است؛ از Flutter، Presentation، Data، دیتابیس، فایل‌سیستم یا شبکه استفاده نمی‌کند. ورودی و خروجی‌ها مدل‌های تایپ‌شده‌اند؛ `Map<String, dynamic>`، eval و اجرای فرمول متنی نداریم.

## اجزا

- `CalculatorCategoryId`: هشت دستهٔ برنامه و `CalculatorCategory` برای توضیحات فارسی/انگلیسی.
- `CalculatorDefinition`: شناسهٔ پایدار، دسته، نام‌ها، توضیح، نام‌های جایگزین، فیلدها، فرمول LaTeX نمایشی، فرض‌ها، مثال‌ها و واژه‌های مرتبط.
- `InputFieldDefinition`: union بستهٔ سه نوع `NumericFieldDefinition`، `ChoiceFieldDefinition` و `NumberListFieldDefinition`.
- `RawCalculatorInput`: ورودی خام تایپ‌شده؛ متن یک فیلد یا فهرست ساختاریافتهٔ متن اعداد.
- `CalculatorInput`: مقادیر عددی/انتخابی/فهرستی پس از نرمال‌سازی.
- `CalculatorParameters`: قرارداد marker برای کلاس ورودی مستقل هر موتور. موتورهای بعدی باید کلاس immutable مخصوص خود را پیاده کنند.
- `CalculatorEngine<I>`: قرارداد مستقل هر ماشین‌حساب؛ `bind` برای تبدیل ورودی عمومی به `I` و کنترل فرض‌های بین فیلدها، سپس `calculate(I)`.
- `CalculationResult`: معیار اصلی، جزئیات، هشدارها و تفسیر. مقدار معیار عدد، متن یا فهرست عددی است.
- `CalculationOutcome`: فقط `CalculationSuccess` یا `CalculationFailure`، نه null یا نتیجهٔ ساختگی.
- `CalculationIssue`: کد پایدار، پیام فارسی، شناسهٔ اختیاری فیلد و اندیس اختیاری عضو فهرست.
- `CalculatorExample` و `RelatedTerm`: محتوای آموزشی تایپ‌شده؛ مثال می‌تواند نتیجهٔ موردانتظار داشته باشد.

## ترتیب اجرای اجباری از UI آینده

```text
RawCalculatorInput
  → InputNormalizer.normalize(definition, raw)
  → CalculatorInput یا خطاهای فارسی
  → CalculatorEngine<I>.bind(input)
  → BoundInput<I> یا RejectedInput<I>
  → CalculatorEngine<I>.calculate(parameters)
  → CalculationSuccess یا CalculationFailure
```

`CalculatorRunner<I>` همین ترتیب را اجرا می‌کند. اگر نرمال‌سازی شکست بخورد، حتی bind فراخوانی نمی‌شود. اگر اعتبارسنجی بین فیلدها شکست بخورد، calculate فراخوانی نمی‌شود. شناسهٔ موتور باید با تعریف یکسان باشد. خطاهای پیش‌بینی‌شده باید صریحاً به‌صورت failure برگردند؛ خطای غیرمنتظره به پیام عمومی فارسی تبدیل می‌شود و امکان گزارش آن به diagnostics از طریق callback وجود دارد، بدون نمایش stack یا اطلاعات داخلی به کاربر. خطای callback تشخیصی نیز نباید به UI نشت کند.

## قرارداد اعداد، درصد، واحد و مقدار اولیه

- منبع نرمال‌سازی عدد همان `core/utils/persian_numbers.dart` مرحلهٔ قبل است.
- ارقام فارسی، عربی و لاتین، ممیز نقطه/`٫`، منفی معمولی/`−` و هزارگان صحیح پذیرفته می‌شوند.
- مقدار، بازه و default فیلد درصدی در **واحد نمایشی درصد** هستند: default برابر ۹۰ یعنی ۹۰٪. مقدار موتور پس از نرمال‌سازی **۰٫۹** است. تبدیل دوباره در engine اشتباه است.
- صفر و منفی به‌طور عمومی ممنوع نیستند؛ min/max و موتور هر ابزار تصمیم می‌گیرند. محدودیت‌های بازه inclusive هستند. فرض‌های مخصوص نرخ مالی یا تقسیم بر صفر در موتور مربوط باید کنترل شوند.
- خروجی درصدی `NumericResultValue` نیز نسبت است؛ UI آن را برای نمایش در ۱۰۰ ضرب می‌کند. برای نمونه مقدار `0.8379` باید ۸۳٫۷۹٪ نمایش داده شود.
- unit در این مرحله برچسب تایپ‌شدهٔ متنی است، نه موتور تبدیل ابعاد فیزیکی. ورودی‌ها در واحد اعلام‌شده‌اند؛ تبدیل واحد خودکار یا تبدیل ارز انجام نمی‌شود. اگر انتخاب واحد لازم باشد، فیلد choice جدا و تبدیل صریح در موتور مربوط اضافه خواهد شد.
- default فقط وقتی کلید فیلد در ورودی نیست اعمال می‌شود. پاک‌کردن صریح فیلد با متن خالی هرگز default را برنمی‌گرداند؛ required خطا می‌دهد و optional از مقادیر نرمال‌شده حذف می‌شود.
- فهرست اعداد ساختاریافته است؛ از split کردن کاما استفاده نمی‌کند چون کاما می‌تواند هزارگان باشد. در خطای هر عضو، اندیس داخلی صفرمبنا و پیام کاربر یک‌مبناست.
- متن گزینهٔ نمایشی ورودی engine نیست؛ شناسهٔ پایدار گزینه، مثل `simple`، ذخیره و اعتبارسنجی می‌شود.
- نام و شناسهٔ فیلدها قابل اجرا نیستند. فرمول LaTeX صرفاً دادهٔ آموزشی است و تغییر آن نتیجهٔ موتور را عوض نمی‌کند.

## ایمنی مدل‌ها

سازنده‌ها پیکربندی ناسالم را با `ArgumentError` رد می‌کنند: شناسهٔ نامعتبر/تکراری، بازهٔ معکوس، default نامعتبر، گزینهٔ خالی یا ناموجود، NaN/Infinity، failure خالی و مثال با ارجاع ناشناخته. این خطاها خطای توسعه/تعریف کاتالوگ‌اند، نه مسیر عادی خطای کاربر. خطاهای ورودی کاربر به‌صورت outcome فارسی برمی‌گردند.

فهرست‌ها و mapها defensive copy و unmodifiable هستند؛ تغییر collection اصلی بعد از ساخت مدل روی مدل اثر نمی‌گذارد. مدل‌ها فعلاً equality مبتنی بر identity دارند؛ serialization، migration و مقایسهٔ value-based به این مرحله اضافه نشده‌اند.

## مرز این مرحله

فرم عمومی (مرحلهٔ ۶)، موتورهای واقعی OEE/NPV/Cp (مرحلهٔ ۷)، کاتالوگ کامل، ماتریس تصمیم و گراف پروژه در این مرحله پیاده نشده‌اند. مدل‌های ورودی ساختاریافتهٔ جدید برای مراحل مربوط اضافه می‌شوند؛ نباید به اجرای کد دلخواه یا فرمول رشته‌ای متوسل شد. موتور سادهٔ ضرب فقط در `test/` برای آزمون قرارداد است و در اپ ثبت نشده است.

اکنون OEE، NPV و Cp با موتورهای مستقل به همین قرارداد و صفحهٔ عمومی متصل‌اند. سند `docs/calculators/stage07.md` در ریشهٔ پروژه جزئیات فیلد، فرض‌ها، مثال و تست آن‌ها را توضیح می‌دهد؛ توضیحات «هنوز اضافه نشده» در بخش‌های مرحلهٔ قبل، وضعیت تاریخی همان مرحله‌اند.

## مرحلهٔ ۱۲: شبکهٔ پروژه

`project/project_network.dart` فعالیت immutable با شناسهٔ عددی، مدت و پیش‌نیازهای ساختاریافته، اعتبارسنجی شبکه و گذرهای پیشرو/پسرو را پیاده می‌کند. چهار NumberList هم‌ردیفِ شناسه/مدت و سر/ته یال از فرم به همین مدل bind می‌شوند؛ متن آزاد یا رشتهٔ فرمول اجرا نمی‌شود. NumberList فقط برای فیلد **غیرالزامی** می‌تواند `minItems: 0` و مقدار پیش‌فرض خالی داشته باشد؛ قرارداد فیلدهای قبلی با حداقل یک مورد حفظ شده است. فهرست‌های وابستگی خالی صریح یعنی شبکهٔ بدون یال، نه استفادهٔ مخفی از یال‌های مثال. `project/estimate_moments.dart` کمک‌محاسبهٔ عددی مشترک است، نه موتور فرمول‌محور. هشت موتور پروژه پارامترها و قرارداد مستقل دارند.
